## 3. 实打实的 bug（按风险排序；每条都写「我为什么认为这条代码会被走到」）

### 【P0-1】换台不先把 mytv 拉到前台：`ensure_mytv_foreground` 是死码 —— 风险 ★★★★★｜工量 S

- **现象**：对管家说「换到湖南卫视」，电视没换台，或者桌面/飞牛TV 界面上蹦出一串数字、跳进莫名其妙的页面。
- **位置**：`tvpilot_server.py:591-609`（函数定义）、`:884-917`（`tool_zap`）、`:2344-2345`（注释）
- **触发条件**：`tool_zap` 被调用时，电视前台**不是** `com.tvcam.mytv`（在桌面、在飞牛TV、在 Arcface、mytv 被 LMK 回收）。
- **我为什么认为它会被走到（读数，不是推断）**：
  1. `grep -n 'ensure_mytv_foreground' tvpilot_server.py` → **只有 2 行**：`:591` 的 `def` 和 `:2345` 的一句注释。**0 个调用点**。为排除「注释里的路径其实存在」，我在**运行中的容器**里跑同一条 grep（`docker exec tvpilot grep -n 'ensure_mytv_foreground' /app/tvpilot_server.py`）→ 同样只有 `591` 与 `2345` 两行。**权威树结论一致**。
  2. `:2345` 那句注释原话是「仅在语音换台/管家调用时通过 tool_zap -> ensure_mytv_foreground 唤起」—— 而 `tool_zap`（`:884-917`）的函数体里**从 HOME 到 am start 一行都没有**，`:909` 直接 `zap_via_adb_digits(no)` 注数字键。注释描述的是一个不存在的调用关系。
  3. `heal_loop`（`:2341-2367`）里 mytv 保活巡检已被显式删除（`:2344` 「已禁用」），所以**没有任何旁路**会把 mytv 拉到前台。
  4. **现网读数**：`curl http://192.168.2.200:8090/api/health` → `{"tv_online":true,"adb_connected":true,"foreground_package":"com.mitv.tvhome","mytv_alive":false,"mytv_http_ok":false,...}`。**此刻前台就是小米桌面 `com.mitv.tvhome`，mytv 不在前台**。这条路径不是理论，是现在进行时的默认状态。
  5. butler 侧的期望正好相反：`integrations/tvpilot.py:105-107` 把 `/api/zap` 写成「高层封装：确保 mytv 前台 + 频道归一化 + mytv API」，`core/agent.py:158-162` 在换台后才去 `ensure_foreground("com.tvcam.mytv")` 验证 —— 也就是说 butler **只能事后发现失败，无法阻止数字键打进错误应用**。
- **修法建议**：`tool_zap` 在 `:909` 之前插入 `ensure_mytv_foreground()`，返回 `ok=False` 时直接 `return None, ERR_WRONG_FOREGROUND, ...`，不要继续注数字键。注意副作用（我按「修死路径先量补完会变成什么」的规矩写清）：该函数最坏情况会跑 `30×0.5s + 16×0.5s ≈ 23s`（`:600-607`），**远超 butler 的 10s HTTP 超时**（`integrations/tvpilot.py:36`）→ 必须同时给它一个短超时（例如失败即返），或在文档里把它归到 45s 那一类。
- **工量**：改 1 处 + 定 1 个超时策略，**S（半天内含验证）**。

### 【P0-2】三份「频道名→IPTV 台号」映射互不一致：报得出台号的频道，换台会被拒 —— 风险 ★★★★★｜工量 M

- **现象**：`/api/channels` 列出来、带台号的频道，`/api/zap` 却说「频道 X 没有 IPTV 频道号映射」。用户听得见台号却换不过去。
- **位置**：
  1. `:381-400` `IPTV_CHANNEL_MAP`（模块级，**53 条**）—— `tool_zap` 唯一使用的表（`:905`）；
  2. `:2655-2669` `CHANNEL_NO_MAP`（写在 `/api/channels` handler **函数体内**，**28 条**）—— butler 看到的频道表就是它给的台号；
  3. `:2606-2618` `CHANNEL_NO_REVERSE`（写在 `/api/current` handler 函数体内）—— 反向表，报「现在播的是几台」。
- **触发条件**：任意一次 `/api/channels` → 挑一条 → `/api/zap`。
- **可走到性的读数**（我跑的是脚本，不是手挑）：以 `IPTV_CHANNEL_MAP ∪ CHANNEL_NO_MAP` 为口径比对，**同时出现在「频道表」和「列表接口」却缺席 `IPTV_CHANNEL_MAP` 的有 7 个**：`CCTV-11高清, CCTV-15高清, 国际频道, 睛彩竞技, 睛彩篮球, 睛彩青少, 睛彩广场舞`；其中 **5 个还同时是 `channels.json` 的键**（`normalize_channel` 会放行 → 一路走到 `:905` 才撞墙）：`CCTV-11高清, CCTV-15高清, 国际频道, 睛彩篮球, 睛彩广场舞`。`睛彩竞技/睛彩青少` 两个不在 `channels.json` 里，会在 `:903` 更早一步报「频道表里没有」。
- **更大的分母问题**：`channels.json` 共 **80 个键**，`IPTV_CHANNEL_MAP` 覆盖其中 **52 个**，**28 个（35%）根本换不了**（`:905-907` 直接 `invalid_parameter`）。这 28 个包含 `CCTV-11高清 / CCTV-15高清 / 延边卫视 / 新疆卫视高清 / 西藏卫视高清 / 宁夏卫视高清 / 金鹰卡通 / KAKU少儿 / 世界地理 / 发现之旅 / 风云音乐 …`（完整名单我用脚本算的，可按需出）。另反向不一致：`IPTV_CHANNEL_MAP` 里有 `深圳少儿`，但 `channels.json` 没这个键 → 这条映射是**永远命中不了的死条目**。
  交叉验证 ✅：现网 `/api/health` 报 `channels_count: 80`，与我 `Object.keys(channels.json).length = 80` 一致；现网 `/api/channels` 报 `count: 97`（它读的是 `IPTV_LOCAL_FILE` 那份 m3u，不是 channels.json）→ **对外 97 个频道、可换 52 个**。
- **修法建议**：台号收敛为**单一数据源**（建议放进 `channels.json` 每个键的值里，随只读外挂一起更新），`tool_zap` / `/api/current` / `/api/channels` 三处改为读它；函数体内联的两张表删掉（它们还是每请求重建一遍的开销）。
- **工量**：**M（1-2 天）**：改数据结构 + 三处读取点 + 补测 28 个无台号频道怎么降级。

### 【P0-3】TVPilot 能重启别的容器：`docker.sock` + `docker restart go2rtc`，且该路由无鉴权 —— 风险 ★★★★★（打的是**整机**）｜工量 M

- **现象**：平时看不出来；一旦触发，`go2rtc` 容器被拆建一次（veth/网桥/netns/overlay 变动）。
- **位置**：`docker-compose.yml:14`（`/var/run/docker.sock:/var/run/docker.sock`）+ `tvpilot_server.py:321-323`（`docker cp` 到 `go2rtc:/config/go2rtc.yaml` 后 `docker restart go2rtc`）+ `:3084-3089`（`POST /api/iptv/refresh_rtsp` 起线程直接跑 `_do_refresh_rtsp`）+ `:2927`（该路径在「不要代理给 mytv」白名单里，也就是说它是一条**实打实对外可用的写操作**）。
- **为什么这是清单里最重的一条**：《开发规范》§0 把两次 3.5 小时整机冻结的根因坐实为「**容器崩溃→重建的 churn 触发自研 trim 内核模块死锁**」，§2-7 把「容器频繁崩溃重启」列为真正高危。`docker restart` 正是这个动作。而 `docker-compose.yml:14` 挂的是 **docker.sock** —— 那是宿主机 root 等价能力，不需要这条路由存在就能做出远比重启更狠的事；`tvpilot_server.py:3151` 的 `0.0.0.0:8090` + §2 证明的「**入站零鉴权**」+ CORS `*` 三者叠加，等于**局域网里任何一台设备（包括那台电视上的任意 App）都能驱动 TVPilot 重启别的容器**。
- **修法建议**（不要求你立刻动现网，先给形态）：① 首选去掉 `docker.sock` 挂载，改为让 TVPilot 只写 yaml 文件、由 go2rtc 自己 watch 或运维侧手动重启；② 若必须保留，给这个动作单独加 token（env 下发）+ 只绑 `192.168.2.200` + 从 CORS 通配里排除；③ 无论如何，`/api/iptv/refresh_rtsp` 应加「同一窗口只准跑一次 + 两次之间最小间隔」的闸门 —— 现在 `:3085` 的 `running` 标志只防并发，不防**连发**（跑完就能立刻再跑）。
- **工量**：**M（1 天）**，但**必须排在有意的重建窗口里做**（§0 合并窗口原则）。

### 【P1-4】同一句语音被两个大脑各执行一次：`tv/livingroom/wake` 双头 —— 风险 ★★★★｜工量 M

- **现象**：对着电视说「换到湖南卫视」，可能出现：电视换了台，管家同时又在手机上/音箱上答了一遍；或者两边抢 ADB，前台来回跳。
- **位置**：TVPilot `:2260`（订阅 `tv/livingroom/wake`）→ `:2274-2275` → `handle_wake_command :2151-2179`，其中 `:2168-2171` 本地 `match_channel(command)` 命中就 **直接 `tool_zap(channel)`**；butler 侧 `butler/core/dialog.py:106-112` 对**同一主题、同一 `type=="voice_command"`** 走 `on_wakeup(...)` 进 LLM 大脑（`core/dialog.py:232`）。
- **为什么能被走到**：两边订阅条件我逐条比过 —— TVPilot `:2155-2160` 只处理 `type=='voice_command'`；butler `:108-112` 也是 `vtype == "voice_command" and cmd`。**判据完全重叠，没有任何一方检查 `handled_by`**。而 MQTT 同一主题两个订阅者**都会收到**（不是二选一）。
- **雪上加霜**：`wake` 这条路**绕过了 TVPilot 自己的两道闸**：① 不进 `_action_q`（`:2290` 才是入队口），所以**没有 10s 去重**（`:2284`）；② **不向 `tv/livingroom/result` 发回执**（只有 `mqtt_worker :2241` 发），所以 butler 的 `tv.py:33-36` 按 `request_id` 等的回执永远等不到 —— 虽然 wake 路径 butler 本来也没带 request_id，但意味着**这条链路对账是瞎的**。
- **修法建议**：二选一并写进契约 ——（A）TVPilot 不再订阅 `wake`（删 `:2260`、`:2274-2276`），换台意图全部交 butler；（B）TVPilot 只做「本地能秒换的频道」但**必须先检 `d.get('handled_by')` 或 `source` 字段**并回一条 `result`。我倾向 A（单一决策方，符合 butler 是大脑的定位）。
- **工量**：**M**：删订阅只 3 行，但要先确认现在线上到底靠谁在换台（见 §5「不敢动」第 3 条）。

### 【P1-5】MQTT 网络线程里同步跑 ADB —— 风险 ★★★（条件性）｜工量 S
- **位置**：`handle_wake_command :2171` 在 paho 的 `on_message`（`:2268`，由 `loop_forever :2301` 的网络线程回调）里**直接**调 `tool_zap` → `zap_via_adb_digits`（`:862-881`：N 次 `adb_cmd` + `time.sleep(0.15)`/每条，外加 `get_foreground_pkg :508`）。每条 `adb_cmd`（`:435-440`）都要**先在 `_CMD_LOCK` 里跑一次 `adb connect`**（`:437`，超时 10s）再跑命令，`tool_zap` 全程可轻易耗 5-20 秒。
- **后果**：paho 的网络线程被占死 → 期间不读 socket、不回 PINGRESP → 按 `connect(...,60)` 的 60s keepalive 算，**连续几条慢指令就会掉线**；掉线后 `on_disconnect :2264` 只把 `connected=False`，重连靠 `loop_forever` 自己（异常时 `:2302-2304` sleep 10 重试 —— 退避策略是「固定 10s」，不是 §3-7 说的指数退避，但**至少不会猛拉**）。
- **诚实标注**：现刻 `mqtt_connected: true`，**我没有复现到掉线**。这条的判据是「能走到 + 时长量级」，不是「已发生」。要坐实得看 broker 侧日志（我没动 mosquitto 配置，见 §5）。
- **修法**：`wake`/`face` 分支也只 `_action_q.put(...)`，不要在网络线程里执行。工量 **S**。

### 【P1-6】zap 去重命中时返回「假成功」，butler 照单全收 —— 风险 ★★★★｜工量 S
- **位置**：`:2284-2287` —— 10 秒窗口内相同 `(topic, action, channel, key)` 再来，**不执行任何动作**，却 `publish(MQTT_OUT, {'ok': True, 'duplicate': True, 'request_id': ...})`；butler `integrations/tv.py:78-82` 只看 `result.get("ok")`，**不读 `duplicate`**，于是 `core/agent.py:158` 的验证若恰好也命中旧前台，就会回报「换台成功」。
- **触发条件**：10s 内同一频道连说两次（用户重复一遍、或 ReAct 自己重试）。第二次是**真没换**的 —— 尤其第一次其实失败了（前台被别的 App 抢走）时，重试被去重吞掉。
- **修法**：命中去重时回 `ok: False, error: 'deduped'`（或 butler 侧显式处理 `duplicate`）。二选一，但要**写进 `topics.py` 的契约注释**，否则下一个人还会踩。工量 **S**。

### 【P1-7】`/api/current` 报的不是 mytv，是电信 IPTV 机顶盒 App —— 风险 ★★★｜工量 S

### 【P1-8】口令硬编码 3 份 + ADB 私钥进镜像 → 轮换要改代码重建 —— 风险 ★★★★（属出资人动作，我只给落点）｜工量 S

### 【P2-9】临时文件/缓存无上限（物理读数已在盘上） —— 风险 ★★★｜工量 S
- **TTS 临时文件泄漏**：`:78` `NamedTemporaryFile(delete=False)`，`os.unlink(tmp_path)` **只在成功路径 `:93`**；`:89-90`（`returncode != 0`）与 `:94-95`（audio too small）**直接 return，不删**。
  **物理反证**（当场 ls，不是推断）：`docker exec tvpilot ls -la /tmp` → `tmp60rprr37.mp3 / tmp8j1iunuc.mp3 / tmpd8mefo__.mp3 / tmpuizc24y9.mp3 / tmpzcy405xh.mp3` **5 个 0 字节 mp3 残留**（时间戳 9-17 10:09~11:02）。
- **go2rtc yaml 不删**：`:314-316` 写 `/tmp/go2rtc_refreshed.yaml`，全文 `os.remove` 只出现在 `:470/:481`（截图）和 `:1217`（OCR），**这个 yaml 没有任何删除点**。物理读数：容器内 `/tmp/go2rtc_refreshed.yaml` **74808 字节，mtime Sep 17 10:01**（仍在）。
- **容器 /tmp 总量**：`du -sh /tmp` = **5.4M**，其中 `adb.0.log` **4,958,993 字节，mtime = 我探测的当下（Sep 20 23:45）** ⇒ adb 客户端自己在容器里持续写日志，**永不轮转**，约 2.5MB/天。它落在**可写层**（compose 没给 /tmp 挂 tmpfs），一次重建就没了 —— 但也意味着它会一路涨到容器可写层膨胀。
- **TTS 缓存无淘汰**：`:63-64` `TTS_CACHE_DIR = BASE_DIR/tts_cache`，`:97` 按 md5 写永久文件，**全文没有 size/age 上限、没有 evict 路径**。容器里 `/app/tts_cache` 确实存在（`docker exec ls /app` 读数）。
- **失败截图无保留策略**：`:2446-2455` 每次工具失败写 `data/shot_<tool>_<ts>.png`（持久卷），**只写不删**。当前 `du -sh data` = 1.9M，暂无 `shot_*` 文件（我列了目录）→ 属「越写越大」的潜伏型，不是现在疼。
- **修法**：临时文件用 `try/finally` 统一删；`/tmp` 挂 tmpfs 或让 `adb` 的日志重定向到 `devnull`；tts_cache 加 LRU 上限（如 200MB/30 天）；`shot_*` 保留最近 N 张。**工量 S（半天）**。

### 【P2-10】`ops.jsonl` 不轮转 + 历史查询整文件读进内存 —— 风险 ★★（当前不急，但方向错）｜工量 S
- `:675-698` 追加写；`:701-724` `read_ops_history` **每次把整个文件逐行 `json.loads` 后 `records[-limit:]`** —— `limit=50` 也要全量解析。
- **量化（不夸大）**：现网 `wc -l /vol1/1000/docker/tvpilot/data/ops.jsonl` = **246 行 / 66435 字节**，文件 mtime Sep 21 00:24。⇒ 按当前频率 **不急**（一年也就 1-2MB）。但 `params` 字段会原样存 HTTP 入参（`:684`），含 `input_text` 的文字内容 —— 有隐私留痕问题。
- 另 `:680` 时间戳用 `time.strftime('%Y-%m-%dT%H:%M:%S', time.localtime())` **不带时区**：容器里 `TZ` 未设即 UTC，宿主机是 +0800，跨系统对账时会差 8 小时（《规范》里 alpine 未装 tzdata → 基本可断定 `localtime()≡UTC`，但我没在容器里跑 `date` 验，**这条标未核销**）。
- **修法**：按天/按行数轮转；`read_ops_history` 改为从文件尾部反向读；时间戳统一带 `Z` 或用 `ts_epoch`（`:681` 已经有 `ts_epoch` 了 —— 那 butler 侧就该用它）。

### 【P2-11】`/api/health` 恒 200，电视掉线也算「健康」 —— 风险 ★★★｜工量 S
- `:2744` 起，health 会把 `tv_online / adb_connected / mytv_http_ok / mqtt_connected` 都算出来，但 `make_response(:407)` 只看 `error` → **全 false 也返回 200**。`Dockerfile:23` 的 HEALTHCHECK 见 200 即 healthy。
- **实测读数**：现在 `mytv_alive:false, mytv_http_ok:false` 而 `docker inspect` = `healthy`。
- 后果不是崩，而是**假绿**：出问题时编排层、看板上都是绿的，人误判「服务好好的」。修法：health 里对关键依赖分级（`degraded` 时返回 503 或加 `status` 字段并在 HEALTHCHECK 里判）。工量 **S**。
- 注：`heal_loop :2349` 探测的是 `TV_HTTP(:354)=192.168.2.238:8080`（Arcface），与 `/api/health` 的 `mytv_http_ok`（`:1930` 探 `MYTV_HTTP:10482`）是**两个不同目标**，别把它们当同一件事。

### 【P2-12】`adb_cmd` 用 `cmd.split()` 拆参数 —— 风险 ★★★（正确性，非注入）｜工量 M
- `:435-440` / `:443-449`：`subprocess.run(ADB + ['shell'] + cmd.split())`。
- 两个后果：① **任何含空格/引号的参数会被拆散**（例如带空格的广播 `--es text "a b"` 会变成三个 arg）；② `keyevent`/`tap` 等值来自 HTTP 入参（`:2968-2982`）未经校验就拼进 shell 命令串 —— 因为**没走 shell**（无 `shell=True`），`;`/`|` 只会变成字面参数，**所以不构成命令注入**；但可以让 ADB 收到**多余的位置参数**（语义漂移）。我按「不夸大」的口径写成正确性问题，不写 RCE。
- 另 `:437` 每条命令都 `adb connect` 一次且在 `_CMD_LOCK` 内 —— **电视不可达时每条命令先卡最多 10s**（`:434 adb_ready` 的 `subprocess.run(..., timeout=10)`，且 `adb connect` 对 DOWN 主机要等 TCP 超时），全部工具串行排队 → butler 的 10s 超时**必然全线吃满**。这与 P0-1 叠加会让「换台慢」的现象更难归因。
- 修法：改成 `shlex.split()` 或传 list 参数；把 `adb connect` 挪出热路径（只在 `tv_online()` 失败时重连）并降到 3s。工量 **M（1 天含回归）**。

### 【P2-13】`/api/channels` 依赖一个不在镜像里的文件 —— 风险 ★★｜工量 S
- `:1236` `IPTV_LOCAL_FILE = '/app/data/gd_iptv_source.m3u'`（**硬编码容器内绝对路径**），该文件由 `./data` 挂进来（部署树里存在，18628 字节 mtime Sep 8），**但 `Dockerfile:5-15` 的 COPY 清单里没有它**。⇒ 换机器/清卷后 `:2697` 会走 `except` 返回 500 `read_m3u_failed`，而 `/api/channels` 是 butler 的频道来源。修法：进镜像或在 health 里显式报缺失。工量 **S**。

### 【P2-14】镜像里带三个从未被引用的模块 + 仓库一堆脚手架 —— 风险 ★（杂务）｜工量 S
- `Dockerfile:6-11` COPY 了 `hdmi3_monitor.py / stats.py / alerts.py`，但 `docker exec tvpilot grep -c "import stats\|import alerts\|import hdmi3" /app/tvpilot_server.py` = **0**，`CMD`（`:22`）只跑 `tvpilot_server.py` ⇒ **三个模块是死码**（合计约 286 行 / 22KB 在镜像里）。
- 本地镜像目录还有一批一次性脚本：`patch_alerts.py / patch_cameras_m3u.py / patch_hdmi3.py / patch_hdmi3_routes.py / patch_stats.py / fix_bytes.py / restore_cameras.py / extract_routes.py / test_logo.py / test_logo_v2.py / test_error_matrix.py / data/dbg.py / check_cameras.sh`，以及**重复的 `kill8090.sh` 与 `kill_8090.sh`**（两个都留在根目录）。合计约 65KB（`du -ch` 读数）。它们**都不在 Dockerfile 的 COPY 清单里**（只有 4 个 py 进镜像），所以只污染工作树、不进现网。
- 另 `:122` 与 `:133` 把 `MQTT_IN_FONGMI` 赋了**两遍同一个值**（重复定义，`:130` 注释说明是旧名兼容）。
- 修法：按《规范》§3-5「NAS 代码目录保持干净部署态」，把这些移到 `doc/archive/` 或 `scripts/`。**不给没有 git 的 TVPilot 擅自 `git init`**（前置 §五 红线），所以只能靠挪目录，工量 **S**。

## 5. 我扫不到 / 不敢动的项（明确列出，不臆测）

1. **NAS 部署树比运行码旧 12KB，而下次重建会装它** —— 读数：`/vol1/1000/docker/tvpilot/tvpilot_server.py` 119869 B / md5(归一化) `fa72eadf`，运行容器 `/app/tvpilot_server.py` 131965 B / `676ccbaa`（= 本地镜像一致）。`Dockerfile:5-11` 是 `COPY` 进镜像、`docker-compose.yml` **没有源码卷**，所以「重新 `build`」就会把**旧 12KB 的代码**装上线。《前置》§三 写明 `registry-1.docker.io` 不可达、重建窗口只准 `docker compose up -d` **不加 `--build`** ⇒ 现在靠这条纪律挡住了；但**任何一次破例 `--build` 都会静默回退**。**我没动**（不 rsync、不覆盖），只报。要治就一单：把运行态源码同步回部署树（属写操作，需出资人点头 + 合并重建窗口）。

TVPilot **现在活着且不崩**（重启计数 0、健康检查绿、日志有封顶），端口也没踩系统保留位 —— 这部分放心。
