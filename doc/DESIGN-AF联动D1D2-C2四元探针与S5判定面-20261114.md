## 二、C2 四元探针（契约 §三 S2）

### 2.1 四元取数面（全部为只读，分层避免「要读 adbd 却依赖 adbd」的死循环）

| 元 | 取数命令／面 | 解析 | 失败即 |
|---|---|---|---|
| `network_reachable` | TCP connect `192.168.2.238:5555`（≤1s，不建 adb 会话） | 通＝True／不通＝False | `unknown(reason=network_unreachable)` |
| `adbd_alive` | `adb get-state` → `device`／`offline`／`unauthorized`；辅以 `adb shell getprop init.svc.adbd` | `device`＝running；`offline`/`unauthorized`＝stopped | `unknown(reason=shell_unavailable)` |
| `adb_enabled_setting` | `adb shell settings get global adb_enabled` | `1`／`0`／`null` | `unknown(reason=setting_unreadable)` |
| `last_checked` | 编排时本机时钟 ISO8601 | 必带 | — |

**现读证据**：`tvpilot/adb.py:121-146` `adb_ready()` 用 `adb get-state`＋`adb connect`；`:220-226` `adb_shell_output()` 持久化 shell；`tvpilot/state.py:133-149` `get_screen_state()` 用 `dumpsys power` 的 `mWakefulness`／`Display Power`。仓内**无** `settings get global adb_enabled`／`init.svc.adbd` 现成实现（grep 0 命中），需新写——但本轮只落设计，不落产品代码。

### 2.2 病因判定矩阵（核心：AF-PM 要求「设置被关」vs「adbd 死了」必须可区分）

| # | network | adbd | setting | power | 主值 | reason | 可区分 |
|---|---|---|---|---|---|---|---|
| 1 | True | running | `1` | on | `ok` | — | 基线正常 |
| 2 | True | running | `0` | on | `off` | `setting_off` | ✅ 设置被关 |
| 3 | True | stopped | `1` | on | `off` | `adbd_down` | ✅ adbd 死了 |
| 4 | True | stopped | unknown | on | `off`／`unknown` | `adbd_down(from_baseline)`／`etiology_undetermined` | 依赖基线 |
| 5 | True | unknown | `1` | on | `unknown` | `etiology_undetermined` | ⛔ 猜 |
| 6 | True | running | `null` | on | `unknown` | `setting_unreadable` | ⛔ 猜 |
| 7 | False | — | — | on | `unknown` | `network_unreachable` | ⛔ 猜（病因不可分） |
| 8 | — | — | — | off/standby | `unknown` | `tv_off`（全状态） | §五 |
| 9 | 探测异常／超时 | — | — | — | `unknown` | `timeout`／`probe_error` | fail-closed |

**如实结论（不粉饰）**：`adb_enabled_setting` 本身要靠 adb shell 读，而 adbd 死时 shell 不可用 ⇒ **单靠一次编排探针无法 100% 区分「设置被关」与「adbd 死」**。可区分路径有两条，都必须显式标注证据来源，⛔ 猜：
1. shell 可用时按 #2／#3 直接分型（reason 明确不同）；
2. shell 不可用时**依赖 D2 息屏 24h 的「息屏前四元基线」**分型：基线 `setting=0` ⇒ `setting_off(from_baseline)`；基线 `setting=1` 而现在连不上 ⇒ `adbd_down(from_baseline)`；无基线 ⇒ `unknown(reason=etiology_undetermined)`。

这正是 D2 协议存在的理由，也是契约 §三「unknown 必带 reason、⛔ 缺省/旧值冒充现值」的落点：**基线只作分型证据，绝不冒充现值**。

### 2.3 §五 探测模式约束的落地（⛔ 周期性 ADB 探测）

- 探针函数**无循环、无 sleep、无后台线程、无常驻定时器**；一次调用只读一次四元、只写一个 `last_checked`。
- 只在两处被显式调用：`S8 stage=waking/probing` 编排步进；ADB 相关事件（连接断开／恢复）。
- 息屏态由编排层发布 `unknown(reason=tv_off)`（全状态），**不触发探针**；`result=adb_off_tv_on` 是「电视已亮＋ADB 不可用」，与「息屏不产生 result」两种上下文分开，避免把 `off` 与 `unknown(tv_off)` 混用。
- `adb_ready()` 有 60s 缓存（`adb.py:123-125`），编排内复用即可，⛔ 不额外轮询。

### 2.4 unknown 语义与 stale 阈值建议（写入 discovery attributes）

| 状态 | stale 建议 | 依据 |
|---|---|---|
| S2 `tv_adb_health` | 300s | 覆盖 240s 全链预算，编排中不转 stale |
| S1 `tv_power_state` | 120s | 事件即推 |
| S3/S4 | 60s | 编排步进即推；S4 读不到 `unknown+reason`，⛔ 猜 |
| S5 `tv_arcface_state` | 90s | 事件＋编排步进 |
| S6 `tv_faceid_last` | 600s | 单条覆盖（`retention=last`），不依赖 stale 淘汰 |
| S8 `morning_news_stage` | 与编排同步 | 终态时 done/failed |

`reason` 枚举（不扩契约，只作实现取值）：`tv_off`／`adb_off`／`network_unreachable`／`shell_unavailable`／`setting_unreadable`／`etiology_undetermined`／`arcface_down`／`capture_failed`／`timeout`／`stale`／`probe_error`。超出需报 AF-PM 裁定（§十）。

## 三、S5 判定面设计（`tv_arcface_state`）

### 3.1 取数面（现读证据）

- `tvpilot/config.py:38` `ARC_BASE = http://192.168.2.238:8080`（env 可覆盖）；`tvpilot/routes/ask.py:8` 同址，`/api/ask/*` 转发，失败返回 `arcface_unreachable` 502。
- tvdesk 仓只读盘点：`app/src/main/java/com/tvcam/mytv/launcher/ArcfaceClient.kt:32` `BASE = http://127.0.0.1:8080`（设备本机视角）；`:19-22` 实测 `/api/health` ~148ms、冷启动到 HTTP 可用 ~2.3s；`:101-108` `isHealthy()` 判据＝GET `/api/health`，body 含 `"status"` 且含 `ok`；`:33-34` `PKG = com.example.arcfaceandroid`、`.TvMainActivity`。
- `tvpilot/health.py:33-76` **不查 ArcFace**（只查 adb/iptv/mqtt/docker_sock/wake_local）⇒ S5 需新建判定，C5 结论不变。

### 3.2 主判定（HTTP，不碰 ADB shell）

| HTTP 结果 | S5 | reason |
|---|---|---|
| 200 且 body 含 `"status"`＋`ok` | `running` | — |
| 200 但 body 非 ok | `stopped` | `arcface_unhealthy` |
| 连接拒绝／端口未监听（网络可达） | `stopped` | `arcface_not_listening` |
| 超时（≤1s） | `stopped` | `arcface_timeout` |
| 本机网络异常／DNS／解析错误 | `unknown` | `arcface_probe_error` |

`stopped`（明确不可达）与 `unknown`（探测本身失败）分开，⛔ 把失败伪装成 stopped。只在 `stage=arcface_ensuring` 编排窗口内调用一次；失败后 `am start -n com.example.arcfaceandroid/.TvMainActivity` 拉起，预算内二次探活；仍 stopped ⇒ `arcface_fail`（按裁定①跳过个性化后续步、电视保持开着）。⛔ 常驻探测、⛔ 作触发源。

交叉佐证（事件时，可选）：`adb shell pidof com.example.arcfaceandroid` 有 pid 佐证 running，**只作 evidence，不覆盖 HTTP 判定**。

### 3.3 隐私硬边界（§六＋G3＋裁定②）

- S5 **绝不读 `/api/scan/latest`**：tvdesk `ArcfaceClient.kt:110-129` 该端点含 `faces`／`persons`／`freshMs`，属人脸侧数据；契约 §六禁止人脸原始数据/特征向量进 MQTT／仓库／持久化。
- S5 只发布 `running/stopped/unknown + reason + last_checked`；**不发任何识别结果**。
- faceid 识别结果只由 S6 单条覆盖 `who+at+source`（`retention=last`）；`/api/face/backup` 持久化端点一期链路不调用，列 D1 鉴权收口清单（G3 报备在案）。
- 离线验证脚本显式断言「探针 URL 列表只含 `/api/health`，不含 `/api/scan/latest`」。

## 四、G6 硬要求：每 2h 现读的「读后屏幕态」自证

### 4.1 记录结构（每次现读一条，落盘报告）

```
{seq, at, experiment=true,
 quad_before:{network_reachable, adbd_alive, adb_enabled_setting, last_checked},
 screen_before:{wakefulness, display_power, screen_on},
 quad_after:{...},
 screen_after:{wakefulness, display_power, screen_on},
 screen_changed: bool,
 verdict: "continue_2h" | "degrade_two_point",
 degraded: bool, degraded_reason: "probe_wakes_screen" | null}
```

- 屏幕态取数面：`tvpilot/state.py:133-149` `get_screen_state()`（`dumpsys power`），现前／现后各一次，比较 `wakefulness` 与 `display_power`；`Asleep→Awake` 或 `OFF→ON` 即 `screen_changed=true`。
- 窗口标注：`experiment=true`＋出资人在场授权；结束即停；常态严守 §五「只在编排时＋ADB 事件时更新」。

### 4.2 降级触发（AF-PM 硬要求）

任一回合 `screen_changed=true` ⇒ **现读会唤醒屏幕，实验污染自身** ⇒ 立即停止每 2h 现读，退「两点式回退」（仅息屏前基线＋24h 唤醒后一次现读），并在报告写 `degraded=true, reason=probe_wakes_screen, degraded_at_seq=N`，如实记录降级，⛔ 隐瞒。分型结论强度下降需接受（G6 回退口径已在案）。

### 4.3 离线验证覆盖

验证脚本构造 `Asleep→Asleep`（继续）、`Asleep→Awake`（降级）、`display OFF→ON`（降级）、`Awake→Awake`（继续）四组，断言降级触发正确。真机实测仍等窗口。
